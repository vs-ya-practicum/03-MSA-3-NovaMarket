## Решение

Выбран паттерн CQRS.

`Order Service` остаётся обработчиком команд, изменяющих заказ. `Order History Service` обрабатывает запросы истории покупок. Он потребляет события заказа из существующего топика `order` Kafka и сохраняет проекцию истории покупок в собственной `Order History Database`.

`Order Service` публикует события создания и изменения заказа. Поэтому проекция содержит данные, необходимые для списка заказов и деталей заказа, включая финальные статусы «Доставлен» и «Отменён».

Для `Order History Database` выбран PostgreSQL. Данные проекции заказа имеют стабильную структуру. PostgreSQL поддерживает транзакции, уникальные ограничения для идемпотентной обработки событий и запросы истории покупок по покупателю и дате заказа.

В базе данных применяется Row-Level Security (RLS) по `buyerId`. Она дополнительно к авторизации в `Order History Service` не позволяет запросу получить заказы другого покупателя при ошибке в запросе сервиса.

Мобильное приложение направляет запросы истории покупок через NGINX в `Order History Service`. Запросы списка и деталей не вызывают синхронные запросы к нескольким сервисам.

Для остальных действий используются существующие владельцы функций: `Product Catalog Service` обрабатывает отзыв, а `Shopping Cart Service` добавляет товары для повторного заказа. Проекция истории покупок содержит данные для скачивания чека.

### Альтернативы

| Альтернатива    | Преимущества                                                    | Недостатки                                                                                                                                                                       |
| :-------------- | :-------------------------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| API Composition | Не требует отдельной проекции истории покупок.                  | Ответ формируется только после получения данных от всех вызываемых сервисов. Если один из них отвечает медленно или недоступен, пользователь не получит историю покупок вовремя. |
| Event Sourcing  | Сохраняет полную последовательность изменений состояния заказа. | Для сценария истории покупок требуется только быстрая read-модель. Event Sourcing добавляет хранение событий и сложность восстановления состояния.                               |
| MongoDB для `Order History Database` | Гибко хранит документные данные. | Данные проекции заказа имеют стабильную структуру, поэтому гибкость схемы не даёт преимущества. PostgreSQL предоставляет нужные транзакции, уникальные ограничения и запросы. |

**Недостатки, ограничения, риски**

- История покупок обновляется асинхронно, поэтому между изменением заказа и обновлением проекции возможна задержка.
- `Order History Service` и его база данных требуют отдельного развёртывания и сопровождения.
- События заказа должны содержать данные, необходимые для обновления проекции истории покупок.
- `Order History Service` подтверждает Kafka offset только после сохранения проекции. После недоступности сервис обрабатывает непрочитанные события, начиная с последнего подтверждённого смещения.
- Обновление проекции должно быть идемпотентным, чтобы повторная обработка события не искажала историю покупок.

### Реестр событий для истории покупок

| Шаг | Продюсер      | Причина действия продюсера          | Событие                                  | Консьюмер             | Причина действия консьюмера                                                        | Топик   | Тип события  |
| --- | ------------- | ----------------------------------- | ---------------------------------------- | --------------------- | ---------------------------------------------------------------------------------- | ------- | ------------ |
| 1   | Order Service | Подтверждает заказ.                 | `OrderConfirmedEvent`                    | Order History Service | Создаёт проекцию заказа для истории покупок.                                       | `order` | domain       |
| 2   | Order Service | Отменяет заказ после ошибки оплаты. | `OrderCancelledAfterPaymentFailureEvent` | Order History Service | Устанавливает в проекции статус «Отменён».                                         | `order` | compensation |
| 3   | Order Service | Изменяет статус заказа.             | `OrderStatusChangedEvent`                | Order History Service | Обновляет в проекции статус и данные заказа, включая ссылку на чек при её наличии. | `order` | domain       |
